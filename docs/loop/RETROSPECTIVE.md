# Loop Execution Retrospective

## Observed failure

Issue #1은 완료 조건이 남아 있는데도, 문서 커밋이나 상태 보고 뒤에 다음 미완료
태스크가 실행되지 않았다.

## Structural causes

1. `WORKFLOW.md`는 규칙 문서일 뿐 실행 상태 기계나 작업 큐가 아니다.
   `STATE.md`의 `current task`와 `next action`은 다음 명령을 자동으로 실행하지 않는다.
2. 작업자가 커밋 후 응답을 끝내면 실행 컨텍스트도 끝난다. 별도 백그라운드 실행기나
   재개 트리거가 없다.
3. 문서·상태 갱신을 코드 태스크와 별개의 완료 단위로 취급했다. 이슈의 실제 완료 조건과
   커밋 단위가 분리됐다.
4. 테스트 실패와 데이터 오류를 현재 태스크의 진단·수정 루프로 다루지 않고,
   blocker 또는 보고 종료로 처리했다.
5. `진행 중`이라는 상태 표현이 실제 실행 중인 프로세스와 연결되지 않았다.

## Impact

- Issue #1은 정적 네트워크 데이터와 Dijkstra 골격만 추가된 상태인데, 여러 문서 커밋이
  완료처럼 보이게 했다.
- 사용자는 작업이 계속 실행된다고 오해할 수 있었고, 실제 구현 진척을 확인하기 어려웠다.
- 원본 XLSX 파싱 오류가 다음 태스크가 아닌 현재 태스크 안에서 즉시 해결되지 않았다.

## Required improvements

1. 이슈마다 기계 판독 가능한 태스크 상태(`pending`, `active`, `verify`, `done`,
   `blocked`)와 완료 증거를 둔다.
2. `done` 전환은 지정된 테스트·검증 명령의 성공 결과와 커밋 SHA가 있을 때만 허용한다.
3. 커밋 후에는 첫 `pending` 태스크를 자동으로 활성화하는 실행 주체 또는 명시적 재개
   명령이 필요하다. 응답 종료를 작업 종료로 해석하지 않는다.
4. 실패는 기본적으로 같은 태스크의 `diagnose` 상태로 되돌린다. 라이선스·권한·원본
   접근처럼 작업자가 해결할 수 없는 경우만 `blocked`로 둔다.
5. 문서 변경은 해당 코드·데이터·테스트 변경과 같은 커밋에 포함한다. 독립 문서 커밋은
   이슈 범위 또는 실행 시스템 자체를 바꾸는 경우에만 허용한다.
6. `진행 중`은 실제 실행 프로세스 ID 또는 활성 작업자가 있을 때만 표시한다. 그렇지
   않으면 `next action`으로 표현한다.

## Issue #1 corrective action

현재 이슈는 `T1 정적 네트워크 데이터` 다음 단계부터, 최소 유효 파일 묶음마다
테스트 → 커밋 → 다음 태스크 실행 순서로 진행한다. 각 커밋은 이 문서의 개선 규칙을
따른다.
